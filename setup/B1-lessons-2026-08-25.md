# B1 lessons — draft board, scouting schema, ratings scale

**rev 001 · 25 Aug 2026 · role: lessons record · authority: derived**

B1 (baseball draft parser + prerequisites) is complete and closed out. MLB6, MLB8, and MLB21
have all run their drafts through the pipeline; `bb_drafts.status` correctly reads `'complete'`
for finished drafts; the draft board view is live and sorts correctly for DaDaBIK's single-column
sort limit. This is the lessons capture for that arc, written the way `lessons.md` captures
football's — root causes and the governing principle behind each, not just a bug list. A found
bug gets fixed or logged; a document is not evidence anything was fixed, only the file is (this
one's fixes are all confirmed live against the database, not just against a pasted gate report).

## Governing principle carried over from football, reconfirmed here

When someone (including Alan, including me) asserts something, the default response is a query to
validate it, not acceptance. Every migration this arc — r007, r008, the ratings ×10 backfill —
was pre-verified live against the database with a `WITH ... AS (...)` CTE wrapping the planned
view body *before* being handed over, not just reasoned through. That discipline caught a broken
GATE 5 subquery before delivery. It's cheap insurance and it stays standard practice for B-series
work.

## Design for the business you actually have, not the one you copied from

The biggest single course-correction this arc: `bb_draftee_scouting` was built with
`UNIQUE KEY (draftee_id, scouting_franchise_id)`, carried over from football's D8 design where
scouting genuinely is per-franchise-private. Baseball on this project isn't — it's family-only
(a separate site handles all-coaches baseball), and a scouted value is the same no matter who
submits it. That mismatch produced two increasingly elaborate view-layer workarounds (row
fan-out, then a scout_a_/scout_b_ pivot) before Alan asked the right question: *"Is there a reason
we're not just upserting the data when we scout the 2nd time?"* The fix was one line of schema —
`UNIQUE KEY uk_scouting_draftee (draftee_id)`, franchise_id kept only as provenance — and it made
both prior view workarounds unnecessary. Lesson: when a view keeps needing another layer of
cleverness to cope with duplicate rows, stop and ask whether the *schema* is describing the wrong
shape, before building a third layer.

## DaDaBIK views need explicit post-install configuration, every time

A plain SQL view has no PRIMARY KEY DaDaBIK can infer. After installing or replacing one:
1. Set the unique field by hand (`draftee_id` here) — DaDaBIK won't guess it.
2. Run DB Synchro if the column list changed (added/renamed/dropped a column) — DaDaBIK caches
   its own schema copy and a value-only change doesn't need a fresh sync, but a column change does.
3. DaDaBIK's table browser sorts on exactly one column. Where the desired order spans multiple
   logical fields (League → Season → draft-row order here), the fix is a single computed VARCHAR
   column concatenating the fields with zero-padded (`LPAD`) segments and a separator that sorts
   after all alphanumerics (`|`), so string-sort order matches the intended order.

This one had its own two-round bug: r007's sort column was constant *within* a draft (only
League/Season/draft_id, and there's only ever one draft per season, so nothing distinguished rows
inside one draft) — Alan caught it live from raw pasted rows. r008 added `draftee_no` as a third
segment and dropped the redundant `draft_id`, confirmed live to match `draftee_no` order exactly
within MLB21.

## Storage precision vs. column type — ask before widening

ASM and GPM ratings were showing as whole numbers only. Root cause: `draft_asm()`/`draft_gpm()`
compute genuine decimal values, but the parser was discarding the fraction with
`(int)round($value)` before writing to `smallint` columns. The fix Alan chose (after checking with
his son, since this is a business-rule call, not a technical one) was **not** to widen the columns
to DECIMAL/FLOAT — keep them whole-number smallints, but store `value * 10` so one decimal place
survives and is recovered by dividing by 10 on display. Both scaled ranges (asm 60-720, gpm
250-410) sit comfortably under `smallint`'s 65535 ceiling. Lesson: "it's rounding away precision"
doesn't automatically mean "widen the column" — ask what the actual display/precision requirement
is before picking a fix, especially when someone else (here: Alan's son, the actual end user of
the ratings) has a stake in the answer.

## The device bridge silently changes file permissions/ownership on push

`mcp__remote-devices__device_commit_files` writes to the live server with different
ownership/permissions than the file had going in — group comes back `alandev` instead of the
project standard `alandev:www-data`, and at least once (`bb_draft_parser.php`) mode came back
`600` instead of the standard `640`. This broke a live page (`require_once` → Permission denied)
and needed a manual `chown`/`chmod` after the fact. Caught wrong once already this arc: I checked
that two drift-affected files matched *each other* and called it fine, when neither matched the
stated standard — Alan corrected that directly. Standing rule for B-series (and beyond): after
every bridge-pushed PHP file, verify ownership/mode against `alandev:www-data` 640 explicitly,
don't just eyeball a sibling file. `bb_draft_parser.php`'s permissions after its second push (the
ratings-write-site change) are confirmed fine by a different route than a fresh `ls -la`: the
turn-21 forced re-run processed successfully through that exact file afterward (24 draft order,
24 round selections, 1 scouting result) — a mode-600/wrong-group file would have thrown the same
`require_once` Permission denied it threw the first time, so a clean run is itself sufficient
proof. Worth remembering as a general check: a live page working end-to-end after a bridge push
is valid confirmation on its own, a separate `ls -la` isn't always needed.

## A completion gate only fires once it's actually deployed

MLB21's `bb_drafts.status` stayed `'in_progress'` despite having all 72 picks, because the
completion-gate code was written and tested earlier in the session but not yet live on the server
when turn 21 was first processed. Not a logic bug — an ordering-of-deploy-vs-data bug. Fix was
mechanical (force-reprocess turn 21 via the existing upload once the gate code was live), but the
general lesson is to check gate-dependent state directly after any mid-session code deploy, for
any turn that was processed before the deploy — "we added a gate" isn't the same claim as "every
row that should have tripped the gate did."
